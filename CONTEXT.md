# Visual Regression Platform

Automated visual regression testing. Projects contain named UnifiedTests (image or PDF kind). Each test captures Screenshots across Variants. A comparison engine detects pixel differences between BASELINE and CURRENT screenshots. Changes are reviewed and approved through the platform.

## Language

**Project**:
A named container for visual regression tests, representing a web application or component library.
_Avoid_: Application, site

**Group**:
An organizational label that bundles Projects for navigation and inbox grouping. Groups do not affect a Project's tests or review state.
_Avoid_: Category, folder, tag

**Branch**:
A named line of development inside a Project. Owns its own UnifiedTests, baselines, comparisons and review state. Every Project has exactly one default Branch (`main` by migration); a feature Branch inherits its target Branch's baseline until the first approval pins the variant to the Branch. Omitting `branch` in an API call means the project's default branch.
_Avoid_: Environment (that is a Variant dimension), fork (that is the baseline clone), promote/merge (branch baselines are never promoted; merging is a Git action that produces a normal review on the target branch)

**Inbox**:
The global queue of pending comparisons across all Projects, grouped by Group. It is the review entry point at `/`.
_Avoid_: Queue, review list

**UnifiedTest**:
A named test belonging to a Project. Has a `kind` discriminator (`image` or `pdf`). Status values: PENDING (no baseline yet), UNCHANGED (baseline matches current), PENDING_APPROVAL (changes await review).
_Avoid_: Snapshot, test case

**Screenshot**:
An image or PDF capture for a UnifiedTest. Two types: BASELINE (accepted reference) and CURRENT (under evaluation). For PDF tests, screenshots store PDF URLs rather than image URLs.
_Avoid_: Image, capture, snapshot

**Variant**:
A screenshot configuration specified by `(viewport, browser, environment)`. A UnifiedTest can have screenshots for multiple variants simultaneously. Screenshots are stored per variant — the `UnifiedScreenshot` table is unique on `(testId, variantId, type)`, so each variant owns its own BASELINE and CURRENT rows. Variants are stored in a separate `UnifiedVariant` table with a reference to the baseline screenshot.
_Avoid_: Profile, configuration, preset

**UnifiedComparison**:
The result of a diff between a BASELINE Screenshot and a CURRENT Screenshot. Status values: PENDING_APPROVAL (differences found), APPROVED (reviewer accepted). A zero-diff comparison is never persisted (see Flagged Ambiguities). Mismatch count: pixels for images, pages for PDF.

**Changed region**:
One contiguous area of an image diff, stored on the UnifiedComparison as `(x, y, width, height, pixelCount)`. Regions are what the review page numbers on the picture and lists beside it, so "where did it change" is answerable without hunting the diff. They are derived by the worker from the diff mask (not by the browser: the stored diff image is not readable back under CORS), ordered largest first, and capped at the 40 largest. `pixelCount` is the exact number of mismatched pixels inside the region's box; regions never nest (one fully inside another is folded into it).
_Avoid_: Diff cluster, hotspot, blob, area

**ComparisonJob**:
An asynchronous queue job that processes a comparison in the background when a CURRENT screenshot is uploaded.
_Avoid_: Task, worker job, message

**ComparisonStatus**:
The status enum on a UnifiedComparison record. Defined in Prisma schema.
_Avoid_: (none)

**ComparisonOutcome**:
The upload API response value. Values: IDENTICAL (hash match — no diff needed), BASELINE_CREATED (first upload became baseline), COMPARISON_QUEUED (hash differs, async diff job enqueued).
_Avoid_: Comparison result

**Threshold**:
A configurable pixel mismatch tolerance per baseline Screenshot. The worker applies it prospectively on image diffs: a mismatch at or below the baseline threshold is auto-accepted — no comparison row and no diff artifact are stored, the candidate is reclaimed, and the baseline is kept (so tolerated differences cannot accumulate; approval remains the only baseline writer). A threshold of 0 (the default) keeps every non-zero mismatch reviewable. When a user updates the threshold, existing PENDING_APPROVAL comparisons with mismatch at or below the new value are deleted (auto-accepted) — the update path and the worker share the same `<=` boundary. The decision lives in `ThresholdPolicy` (`core/domain/policies/threshold-policy.ts`): auto-accept (`decideThresholdAction` for the update path) and the read flag `thresholdExceeded` (`isThresholdExceeded` — strictly above the baseline threshold; the worker accepts when it is false). The rule is single-sourced on the server: the threshold-update endpoint accepts `preview=true` to return how many comparisons a value would auto-accept without mutating, and the frontend confirm dialog is driven by that response instead of re-encoding `mismatch <= threshold`. Threshold changes are admin-only and audited (`test.threshold`, including the previous values and the auto-accepted count). Threshold is image-only: PDF threshold updates are rejected, the PDF DTO no longer exposes `thresholdExceeded`, and the worker never applies the threshold to PDF comparisons. The engine tolerance (`engineTolerance`) is a fixed 0-1 float (0) and is deliberately NOT the business threshold — `pixelDiffThreshold` never reaches the comparison engine.

**Effective threshold**:
The tolerance the worker actually applies. It is the baseline's own `pixelDiffThreshold` when that is greater than 0, else the project default (`Project.pixelDiffThreshold`), else 0. One function (`effectivePixelThreshold`) owns the rule; the worker and the review UI both read it. The project default is set by an ADMIN (`project.pixel-threshold`, audited) and applies prospectively — it does not retire pendings that already exist. **Config-as-code** (`.vrt.json` → upload `pixelDiffThreshold`) may set the value when the upload creates the baseline and may only *tighten* an existing threshold; raising one stays the ADMIN path because raising auto-accepts pendings (ADR-057). An explicit per-variant 0 is indistinguishable from "unset" and therefore inherits the project default.

_Avoid_: Tolerance, limit

**StorageQuota**:
A per-Project cap on stored evidence bytes — BASELINE/CURRENT screenshots and diff artifacts. `null` means unlimited; `0`, negative and non-numeric values are rejected rather than read as "unlimited". Render-cache pages and page-count blobs are not evidence and do not count against it.
_Avoid_: Storage limit, disk quota, plan

**BaselineRevision**:
A replaced baseline kept for restore. Approval and restore write one before overwriting the current baseline; it stores the file URL, hash, page count, threshold, actor and reason. Retention is bounded per variant by `BASELINE_HISTORY_LIMIT` (default 10); pruning happens on write, and a revision's file is protected from the storage sweeps until its row is removed.
_Avoid_: Version, snapshot, backup

**WebhookEndpoint**:
A project-scoped outbound notification target: URL, signing secret, subscribed events and payload format. Managed from the project's settings page; administration requires a browser session (an API key cannot create or edit one).
_Avoid_: Hook, integration, notification channel

**WebhookDelivery**:
One outbox row per event × endpoint. Written in the same transaction as the domain change where one exists, claimed by the worker's dispatcher, retried with backoff, delivered at-least-once and deduplicated by `X-VRT-Delivery-Id`. Claims carry `claimedAt`; a row stuck in PROCESSING for more than 10 minutes is returned to PENDING and redelivered.
_Avoid_: Webhook job, message, notification

**AuditEvent**:
An immutable record of a sensitive action (approval, baseline restore, deletion, webhook change) with actor, action, project/test/branch names, target and metadata. Rows have no foreign keys, so they outlive the rows they name.
_Avoid_: Log entry, history row

**Role**:
The global permission level of a user: `ADMIN` (users, API keys, webhooks, audit, project/branch deletion, review policy and pixel thresholds), `MEMBER` (uploads, approvals, restores, assignments, comments, test/variant deletion) or `VIEWER` (read-only). API keys carry their own scopes (`read`/`upload`/`approve`/`admin`, ADR-035/045): a key with the `admin` scope acts as `ADMIN`, every other key as `MEMBER`. A temporary password (`mustChangePassword`) only unlocks `/auth/*` until changed.
_Avoid_: Permission, scope, group membership

**ReviewComment**:
A plain-text discussion entry on a test, optionally anchored to a comparison. Threads resolve instead of deleting; the read returns the newest 200 (oldest→newest for display). Test/project deletion removes the comments in the same transaction, and a bounded maintenance task cleans historical orphans.
_Avoid_: Note, annotation, message

**ReviewAssignment**:
A review work item: project/branch plus a test or run, an assigned active user, an optional due date and a completion timestamp. Creation and completion require a browser session; the inbox can filter to "my reviews". Overdue is derived from the due date, not stored.
_Avoid_: Ticket, task (the queue job is a ComparisonJob)

**ApprovalVote**:
One reviewer's vote for a comparison in a project whose `requiredApprovals` is greater than 1. Votes are keyed by the stable principal id and recorded with `review.vote`; the comparison stays PENDING until the threshold is reached, then the final approval writes the `Approval` row. API keys cannot vote for N>1 (human-only 4-eyes). Votes are audit: they are never deleted with the test, branch or project, because the surviving `Approval` row cannot reconstruct which reviewers supplied the four eyes (ADR-050). Only `ReviewComment` is removed with its test.
_Avoid_: Approval (that is the final record), review count

**Run**:
A CI run that groups uploads of one Project/Branch, identified by a client-supplied `runKey` and carrying optional commit metadata. Jobs, comparisons and approval audit rows link to it; finishing is explicit (or automatic after 24 h idle). A Run groups and gates work; it does not isolate candidates — latest-wins remains per Variant.
_Avoid_: Build, pipeline, attempt

**RunState**:
The CI gate reading of a Run: `open`, `pending`, `failed` or `passed`, derived from the Run's counts and whether it is finished. The rule has one owner, `run-state.policy.ts` (`decideRunState`), and every reader calls it — the status endpoint the CI action polls, the anonymous share page, and the JUnit/HTML/CSV reports. `failed` wins over `pending`; a Run with nothing left to review and no running job is `passed` once finished (`open` before). A muted UnifiedTest does not hold the gate: `pendingComparisons` still counts it, `mutedPending` is its subset, and only their difference decides `pending`, so the counts explain the gap instead of a second derivation re-inventing it. The same rule reaches the other readers: the JUnit/HTML/CSV reports mark a muted pending comparison as `muted` instead of failing on it, a run's pending row carries `muted`, and "approve all pending" skips those rows rather than approving the work their owner deferred.
_Avoid_: Run status (that is the read DTO), gate result, CI status

## Flagged Ambiguities

- **UnifiedComparison vs ComparisonJob vs ComparisonOutcome**: Three distinct concepts: the persisted result record, the async processing mechanism, and the upload return value.
- **ComparisonOutcome vs ComparisonStatus**: Overlapping but distinct. ComparisonOutcome (IDENTICAL, BASELINE_CREATED, COMPARISON_QUEUED) is the upload API response. ComparisonStatus (PENDING_APPROVAL, APPROVED) is the persisted status on a UnifiedComparison record.
- **Screenshot vs Snapshot**: "Snapshot testing" (Jest) is unrelated — this platform uses pixel-level image comparison. Avoid "snapshot" in this codebase.
- **TestStatus.UNCHANGED vs a comparison's outcome**: `TestStatus.UNCHANGED` means no changes are pending for the test. A zero-diff comparison and an image diff within the baseline threshold are never rows: `createPending` always writes `PENDING_APPROVAL`, and the unchanged path (`ComparisonJobProcessor.handleUnchanged`) and the within-threshold path (`ComparisonJobProcessor.handleWithinThreshold`) retire the candidate and emit a `comparison_completed` observability event with `outcome: 'unchanged'` / `'within_threshold'`. The outcome is therefore an event field (`ComparisonCompletionOutcome`), not a `ComparisonStatus` value — the enum holds only the two statuses a row can actually have (`PENDING_APPROVAL`, `APPROVED`), so it cannot be mistaken for "no comparison was run". The aggregate `resolveAggregateStatusFromVariantStatuses()` (used to persist the test row) is derived from the same per-variant rule as the read model, so the two cannot drift — a test with one pending variant and one clean variant is PENDING_APPROVAL on the row while the clean variant reads UNCHANGED (consistent, not contradictory). The variant → status derivation has a single owner: `VariantStore.findVariantStatusSignalsFor` (the query + row mapping), composed by both the persisted aggregate (`TestStatusService`) and the project overview read model (`ProjectReadRepository`).
- **Approval pins the comparison id**: The approve endpoints take `comparisonId`, not a variant. Approval resolves exactly the comparison the reviewer saw and rejects a stale target (no longer PENDING_APPROVAL) with a CONFLICT instead of silently approving whatever is pending at click time. The variant of the approved candidate (used for retirement) comes from the comparison entity, not the request.
- **Variant vs VariantRecord**: `Variant` is a domain value object class with validation and equality (`variant.vo.ts`). `VariantRecord` is a plain interface `{ viewport, browser, environment }` used in job data and event payloads to avoid circular dependencies. Use `Variant.toRecord()` / `Variant.fromRecord()` to convert.

## Implementation Notes

> Architecture decisions live in `docs/adr/`. This section captures only non-obvious design choices that can't be inferred from code structure.

- **Permissions are enforced once, in the auth guard**: the session path loads the user per request and attaches `{ userId, role }`; API keys attach `ADMIN` when their scopes include `admin`, `MEMBER` otherwise. `@Roles('ADMIN')` elevates admin routes, a global rule rejects every non-GET for `VIEWER`, and `mustChangePassword` blocks every route. An API key's capability is declared **on the route** with `@Scope('read'|'upload'|'approve'|'admin')` (a list: any one satisfies it); a route that declares none is not callable by a key at all, so a new endpoint makes the decision instead of inheriting `admin` from a path table (ADR-045). A key with a project allowlist may only call routes that name a project (`projects`, `review`, `groups`, `audit`, `users`, `search` are refused). Both of those last two exempt the **account-lifecycle surface** — the `AuthController`, marked `@AccountLifecycle()` — because a viewer must still be able to sign out and the screen that clears `mustChangePassword` has to stay reachable. The exemption is route metadata, not a path check: keying it off `path.includes('/auth/')` also matched a project, test or run literally named `auth`, which handed a VIEWER write access to that project's routes and bypassed the password gate. Deactivation and password reset delete sessions, and deactivation also revokes the API keys the user owns; the last active admin cannot be demoted/deactivated and an admin cannot deactivate itself. User/permission changes are audited.
- **A project is named, but its identity is the id**: `Project.name` is unique and renameable, and a deleted name is free again. Every live reference stores the id instead: `ShareLink.projectId` is a foreign key (`ON DELETE CASCADE`), `ApiKey.projectIds` holds ids while the API form still says `projectNames` (the guard resolves the request's `:projectName` to an id and compares ids; a `BEFORE DELETE` trigger drops a deleted project from every allowlist), and `Approval`/`AuditEvent`/`ComparisonOutcomeEvent` carry a nullable `projectId` filled by a `BEFORE INSERT` trigger from `projectName`, which stays as the write-time display value — the history reads filter by id (ADR-061). An allowlisted api-key request pays one indexed name→id lookup; an unrestricted key pays none. Creating a key with an unknown project name is a `400`. Cross-row identities the schema cannot express stay application-enforced: `Run.projectId` equal to its branch's project, a screenshot's `testId` equal to its variant's, a comparison's `testId` equal to its baseline's, `Project.defaultBranchId` and `Branch.targetBranchId` inside the same project. Prisma cannot model those composite foreign keys without redundant scalar columns, and a raw-SQL constraint would be dropped by the next schema diff.
- **The TOTP seed is encrypted at rest**: `User.totpSecret` is an AES-256-GCM ciphertext (`v1:<iv>:<tag>:<ciphertext>`) under the required `TOTP_ENCRYPTION_KEY`; a value without the prefix is a legacy plaintext seed that is read as-is and re-encrypted after the next successful TOTP login, and an undecryptable value fails authentication closed rather than reading as "no second factor". `AuthRepository.updateTotpSecret` (the re-encryption) must not clear `totpEnabledAt` (ADR-062).
- **The actor is read, never invented**: controllers obtain the caller through `requireActor(req)` (the display name for audit rows) or `requireUserActor(req)` (the signed-in user's stable id, for routes that act as a person — comment authorship, assignments, user administration). Both live in `common/http/authenticated-principal.ts` and throw `401` when the principal is missing. There is deliberately no `?? 'unknown'`/`?? 'admin'` fallback: an audit row naming someone who did not act is worse than a failed request, and the fallback hid a guard that had stopped attaching `auth`. The signature carries the rule too: a service method that records an actor declares `actor: string`, never `actor?: string`, so a controller cannot pass `req.auth?.username` without the compiler rejecting it (twelve call sites still did, which is why the helper alone was not enough).
- **A Run is grouping, not isolation**: the upload resolves its Run inside the same `StateChangeWorkflow` transaction (no key = no run, exactly the old behavior), and every upload into a finished run reopens it. `ComparisonJob`, `UnifiedComparison` and `Approval` carry the denormalized `runId`/`runKey`, so a run's status can be derived after comparisons are deleted on approval. Status is computed from counts (pending comparisons, pending/processing jobs, failed jobs, approvals), never maintained as a counter, and its derivation has one owner (`run-state.policy.ts`, see **RunState**): `failed` wins over `pending`, muted comparisons do not hold the gate, a clean finished run is `passed`, a clean unfinished one is `open`. The run does NOT make parallel uploads safe — two uploads for the same variant still supersede each other. The `RunAutoFinishTask` closes runs idle for 24 hours with `finishedBy = 'auto'`.
- **Audit rows ride the mutation's transaction**: `AuditService.record` writes through the ambient transaction, so a mutation never commits without its trail. Every write path that records one opens that transaction explicitly — approval, restore, deletion, threshold, comment (with its webhook outbox row), assignment (with its outbox row), share-link create/revoke, webhook endpoint create/update/delete, user create/update/reset and the project settings writes (retention, rename, review policy) — instead of writing the row "right after" the change and hoping. The rule is asserted, not documented: `AuditService.record` calls `TransactionContext.assertInTransaction()`, and the one legitimate exception is named — `recordAccess(entry)` for opening a share link, which is a read and must not fail for lack of a transaction. The other half is the write it rides: a repository taking part in such a transaction must extend `BaseRepository`, whose `client` follows the ambient transaction. `ReviewAssignmentRepository` and `ShareLinkRepository` took `PrismaConnection` directly, so their rows committed outside the audit's transaction and a rollback left half a change behind. `WebhookDeliveryRepository.createMany` asserts it is inside a transaction; the endpoint test button's single row deliberately does not, because it has no domain change to ride. Reads are filtered and paginated in one query; the CSV export is a bounded snapshot (10k rows). A repository that writes inside one of those transactions must extend `BaseRepository`, whose `client` follows the ambient transaction — `AuthRepository`, `ReviewAssignmentRepository` and `ShareLinkRepository` took `PrismaConnection` directly, so their rows committed outside the audit's transaction. `ComparisonOutcomeEvent` is the deliberate opposite: it is a report written outside the comparison transaction, and `ComparisonOutcomeService.record` never throws, so a lost trend row cannot fail a job whose comparison already committed. A mutation whose trail scales with its input writes it in one INSERT: `AuditService.recordMany` is the batched counterpart of `record` (same ambient-transaction assertion) and is used by whole-project deletion, which writes one row per test. The durable `Approval` record and the API keys' own `createdBy`/`revoked*` fields stay as the detailed source for those actions — the audit trail is the cross-project view, not a replacement.
- **Webhooks are an outbox, not a post-commit call**: `WebhookDispatchService` writes `WebhookDelivery` rows for the subscribed endpoints inside the same `StateChangeWorkflow` transaction as the pending comparison (`review.requested`) or the approval (`comparison.approved`). The worker-only `WebhookDispatcher` claims due rows with `FOR UPDATE SKIP LOCKED`, signs `timestamp.body` with the endpoint secret, sends, and retries with backoff; the API process never performs outbound webhook I/O. Delivery is at-least-once and ordered only by row creation, so consumers deduplicate on `X-VRT-Delivery-Id`. Payloads carry a dashboard link built from `APP_PUBLIC_URL`, never a presigned storage URL. Administration is session-only (`@SessionOnly()` on the controller): a CI API key cannot register or edit an endpoint. `job.failed` is deliberately missing from v1 — the queue's failure path owns its own write and needs an observer seam before it can emit (see ADR-029).
- **Branch scope and inherited baselines**: `UnifiedTest` belongs to exactly one Branch (`@@unique([branchId, name])`); the Project is reached through `branch.project`, so every downstream row (variant → screenshot → comparison → status → retirement → approval) is branch-scoped without extra columns. Uploads resolve `(project, branch)` through `BranchResolver` and materialize a missing Branch on first upload (`targetBranchId` null = "the project's current default branch"). `BranchBaselineResolver` is the single owner of "which baseline does this variant compare against here": an owned baseline is used as-is, an inherited clone follows the target chain (refreshed on every upload, preserving the branch's threshold), a missing variant clones the nearest ancestor's baseline (`UnifiedVariant.isInherited = true`), and a disappeared target baseline pins the clone (`isInherited = false`) instead of deleting it. Approval flips the variant to owned, so a feature branch only ever writes its own baseline. Reads use a recursive-CTE "Branch View" (`BranchTestRepository.findEffectiveTests`) that surfaces unmaterialized ancestor tests as `origin = "inherited"`; those are read-only in the branch context (mutations answer `409 CONFLICT`). The inbox never reads through — it lists real pending comparisons with their owning branch. Branch deletion cascades to its tests and reclaims only URLs no surviving row references (an inherited clone shares its file with the target).
- **Inbox, project list and groups**: `/` is the review inbox (cross-project pending comparisons), `/projects` is the Project list, and Groups are organizational only — they do not scope a Project's tests or review state.
- **Upload transaction boundary**: Storage (RustFS) outside DB transaction with compensating delete on failure. Domain events are emitted after commit as direct observability (logger + metrics) — there is no event bus or outbox table (see ADR-004). Comparison jobs are enqueued inside the same transaction. The upload decision is atomic with the write for the stored paths: `resolveTestAndBaseline` runs transaction-ambient and the store + write re-resolve inside one retried Serializable transaction. The identical fast path re-resolves inside its own retried Serializable transaction and falls through to the stored path if a concurrent baseline replacement lands in between (latest-wins).
- **Identical-upload vs queued-job race**: The identical path cancels pending jobs and retires the CURRENT candidate row to keep the "at most one reviewable comparison per Variant" invariant. If it interleaves with a different upload that already returned `COMPARISON_QUEUED`, that client's job is silently cancelled and its file reclaimed — the response said queued but the comparison never materializes. This is inherent to latest-wins and accepted: cancelling is the only safe choice (a stale diff could otherwise resurrect a comparison after the identical upload). The window is narrow and the platform stays consistent.
- **StateChangeWorkflow**: The upload, diff strategies and approval handlers run their transactional writes through `StateChangeWorkflow.executeStateChange()` (in `core/application/services/`). It runs the change inside a retried Serializable transaction, recomputes affected test statuses in the same transaction, and emits observability (logger + metrics) + deletes stale files only after commit (in `onSuccess`), forwarding compensating actions to `onFailure`. Mutations declare their outcome via `PersistedChange.events` — a discriminated union of `ObservabilityEvent` records (`common/domain/observability-event.type.ts`) that the workflow switches on to log/metric synchronously. The flush-after-commit invariant lives in one place rather than being re-derived per handler. The ambient-transaction contract is enforced, not documented: transaction-riding mutations (`ComparisonRetirementService`'s `supersedeForVariant`/`supersedeIdenticalForVariant`/`retireSiblingsAndDeleteCandidate`/`createPendingForVariant`/`retirePendingComparisons`/`retireComparisonsForScreenshots`, and `IJobProducer`'s `enqueue`/`cancel*`) call `TransactionContext.assertInTransaction()` before writing, so a caller that escapes the workflow transaction fails loudly instead of silently riding the bare connection.
- **PDF approval reclaims the diff artifact and the candidate row**: Unlike image approval (which deletes the comparison + candidate), a PDF approval keeps the APPROVED comparison row as history but deletes the diff.pdf file and clears its `diffPdfUrl` (`ApprovalService.completePdfComparison` → `UnifiedComparisonsRepository.clearPdfDiffUrl`). The frontend renders the diff only while a diff URL exists; an approved comparison shows "Diff removed after approval" instead. Because the approved comparison is kept, its `candidateId` is detached (set to null — the column is nullable) and the CURRENT screenshot row is deleted once its content has been folded into the baseline. This stops a later upload from upserting the CURRENT row in place and silently re-pointing the approved comparison's `candidateId` at never-approved content.
- **One reviewable comparison per variant is a database guarantee**: `ComparisonRetirementService` still retires the superseded row before writing the new one, but that is a read-then-write. A `BEFORE INSERT OR UPDATE` trigger takes a transaction-scoped advisory lock on the baseline and rejects a second `PENDING_APPROVAL` row, so two concurrent workers cannot both commit; retained approved PDF comparisons on the same baseline are unaffected. The trigger, not a partial unique index, because Prisma would drop an index it cannot model on the next `migrate dev` (ADR-063).
- **SupersededComparison**: A UnifiedComparison (and its files) that a newer candidate must retire so the "at most one reviewable comparison per Variant" invariant holds. The invariant has a single owner: `ComparisonRetirementService` (`core/application/services/comparison-retirement.service.ts`) composes the repository cascade + job cancellation + URL collection, so the side effects stay in one place. Its DB-level cascade lives in `UnifiedComparisonsRepository.retirePendingForVariant(testId, variant, keepComparisonId?)` (`core/infrastructure/repositories/unified-comparisons.repository.ts`) — deletes every PENDING_APPROVAL comparison for the variant (pass `keepComparisonId` to preserve the freshly created/approved one) and returns the stale storage URLs to delete. The threshold path uses the separate `deletePendingByIds`. Candidate screenshot rows are removed by `UnifiedScreenshotRepository.deleteCandidatesAndCollectUrls` (cascade logic lives beside the Screenshot entity). Single-candidate reclamation (a moot worker job, an unchanged diff) flows through `CandidateReclamationService.reclaimCandidateInChange({ testId, candidateId | resolveCandidate, expectedUrl?, events? })` (`core/application/services/candidate-reclamation.service.ts`), which owns the `StateChangeWorkflow` transaction (noop when nothing was reclaimed and no events were emitted) and delegates to the guarded owner — `deleteCandidateIfCurrent` when an `expectedUrl` guards the delete, otherwise `deleteCandidatesAndCollectUrls`; `resolveCandidate` re-reads the row in-transaction (the unchanged-diff race-closer) instead of trusting the payload id. Retirement is variant-scoped for both kinds — uploading to one variant no longer destroys another variant's comparison history. Pending ComparisonJobs are cancelled per variant too (`PostgresJobQueue.cancelPendingForVariant`, which queries dedicated `candidateId`/`variantViewport`/`variantBrowser`/`variantEnvironment` columns on `ComparisonJob` — not the JSON payload). Cancellation happens on the upload and approval paths (both safe: upload enqueues its new job after the cancel; approval replaces the baseline so any still-queued diff would be stale). The worker diff path deliberately does NOT cancel — a queued job belonging to a newer candidate must still run.
- **PDF page count is single-sourced from the pdf-sidecar**: The sidecar's `POST /count` endpoint is the only page-count producer. The upload pipeline (`UploadIntake`, via `PdfSidecarClient`) calls it synchronously during upload and writes the authoritative count to the Screenshot row once; there is no regex fallback and no diff-time overwrite. `PageCountCache` (RustFS + in-memory) is a render-cache concern for page images, not a second count source. Note the count semantics: a comparison row's `pageCount` comes from the sidecar's `/compare` `x-page-count` (pages *compared* = max(baseline, candidate)), which can differ from a screenshot's own document count when baseline and candidate page counts differ.
- **Read responses carry every image URL twice — canonical and presigned**: read DTOs expose the stored URL (`imageUrl`, `diffImageUrl`, `baselineUrl`, `candidateUrl`, `fileUrl`, `newBaselineUrl`) as the stable identity and a `signed*` twin (`signedImageUrl`, `signedDiffImageUrl`, `signedBaselineUrl`, `signedCandidateUrl`, `signedFileUrl`, `signedNewBaselineUrl`) that the browser renders. The canonical URL is what tests/tools compare and what the backend feeds back into `storage.get`; the signed URL is time-limited (`RUSTFS_SIGNED_URL_TTL_SECONDS`, default 3600) and built against `RUSTFS_PUBLIC_URL`, the browser-reachable host. Signing is synchronous (a local HMAC, no I/O) and owned by `S3Presigner` (`internal/storage/services/s3-presigner.ts`, zero-dependency SigV4) behind `IStorageProvider.signUrl`; mappers receive it as a `UrlSigner` function, so mapping stays pure. PDF source URLs (`pdfUrl`, `diffPdfUrl`) are deliberately never signed: they are query inputs to `pdf-render`/`pdf-download` and must stay canonical for ownership checks and `storage.get`. The anonymous-read bucket policy is therefore off by default (`RUSTFS_ENSURE_PUBLIC_BUCKET=false`).
- **Storage-object referencedness is a seam**: "which storage URL must not be deleted" has two shapes — the maintenance sweep's referenced subset (`IStorageObjectReferencedness.findReferencedUrls`, which protects any row reference including a CURRENT row with no comparison) and the reclaim path's reclaimable subset (`filterReclaimableUrls`, which only blocks a baseline-shared or comparison-referenced URL). Both live behind `STORAGE_OBJECT_REFERENCEDNESS` (`common/domain/storage-referencedness.interface.ts`), provided by `StorageObjectReferencednessService` composing the screenshot + comparison repositories, so the internal/data-deletion tasks cross a token instead of importing concrete public repositories.
- **Global lists are server-paginated; the review queue is deliberately complete**: `GET /projects/pending` takes `q` (case-insensitive name search) and `groupId` (the `unassigned` sentinel means "no group"), and `GET /review/pending` takes `q`, `kind`, `groupId`, and `branch`. Both filter and count in the same query, so a page and its `meta.total` cannot disagree. The pending predicate has one owner in two shapes (`core/infrastructure/repositories/reviewable-pending.sql.ts`, moved out of `review/` so the run gate in `core/` can read its complement without a reverse dependency): `reviewablePendingWhere` for the Prisma-filtered inbox page and `REVIEWABLE_PENDING_SQL` for every grouped count, so the badge, the project list and the branch switcher cannot disagree with the queue about muted tests; the archived scope stays with the reader (the queue and the project list exclude archived branches, while the branch switcher's count must stay true when archived branches are explicitly listed). An inbox row carries `projectPendingCount`/`projectBranchCount`, computed per project+branch from the whole pending set rather than the page — the project section's "Review N" describes the set the review pass will walk, and `GET /review/branches` lists every pending branch so pagination cannot hide a filter option. The project detail (`GET /projects/:projectName`) is paginated **by variant row**: `VariantStore.findProjectVariantPage` selects from the shared branch-chain CTE with the table's filters (test-name search, kind, derived status, viewport/browser/environment) and a window count in one statement, so the page and `meta.total` agree on the table's unit; `meta` rides inside the project payload, and `pendingCount`/`testCount`/`filterOptions` are computed from the whole branch set (not the page) so the header and the dropdowns survive pagination. The project list and the inbox use `usePagedListQuery` (one page plus `meta.total`, with a pager); `usePaginatedListQuery` remains only for the pending-test queue, which is intentionally complete — the review pass must see every pending test or it ends at the done page with tests still waiting.
- **Global search is a finder, not a branch read**: it answers "which materialized tests exist" across projects, and every hit carries the branch the test lives on — the palette navigates with that branch, so one name on two branches is two destinations on purpose, while a test that only exists as an inherited shadow has no hit of its own. It excludes archived branches (their tests and the branch rows themselves); "default branch" is read through the project's `defaultBranch` relation, the same fact `BranchResolver` resolves. See ADR-027's named exceptions.
- **Quota is admission control at the stored-write seam, not a ledger**: `StateChangeWorkflow.executeWithStoredFile` requires `charge: { projectName, bytes }` and asserts the project's StorageQuota before `store()` — a stored write that names no charge does not compile, so the two evidence writers (upload intake, diff worker) cannot forget it. `IStorageProvider.putObject` stays policy-free. Only evidence counts: the screenshot `sizeBytes` and comparison `diffSizeBytes` aggregates; the `pdf-render/` cache never crosses the convention and is therefore exempt by construction, not by a flag — bucket usage can exceed the sum of quotas by that namespace, bounded by `PdfRenderCacheCleanupTask`. Enforcement is best-effort: the check reads a cached byte total (`Project.storageUsedBytes`, re-derived from the rows at most once every 5 s, advanced by each admitted charge, always written outside the transaction), so concurrent evidence writes can still overshoot by the concurrency while a deletion or a failed store is corrected at the next re-derive — the byte rows stay the truth; the storage read endpoint keeps deriving exactly because it also reports file counts. A rejection is `QUOTA_EXCEEDED` → 413 with a machine-readable `code`, is non-retryable (a blocked diff fails its job immediately and shows up as a failed job in the Run, rather than retrying three times), and the quota value is validated at the DTO — `null` unlimited, `0`/negative/non-numeric rejected (a stored `0` from before that rule still reads as unlimited, so no existing project is bricked). `JobData` carries `projectName` so the worker can charge its diff artifact. See ADR-043 and ADR-060.
- **Maintenance deletions are storage-first**: `OrphanCleanupService.cleanupCurrentOrphans` deletes storage objects before DB rows (inline in the service via `buildDeletionRecords`), and a row whose storage delete failed is retained so the next maintenance run retries. This is deliberately different from transactional domain deletions (e.g. `TestDeletionService`), which delete DB rows in-transaction and clean storage best-effort post-commit. There are two deliberate exceptions to storage-first: (1) **BASELINE orphan reclamation is row-first** — a BASELINE's object is its live content, and a comparison that re-adopts it between a file delete and the guarded row delete would survive with its object gone; `OrphanCleanupService.cleanupBaselineOrphans` uses `deleteBaselineOrphansByIdsReturningUrls` (guarded DELETE ... RETURNING, shared via `deleteRecordsRowFirst` in `internal/data-deletion/services/deletion-records.ts`) so the file is reclaimed only for rows actually deleted, and a leaked object is caught by the unreferenced sweep. (2) **`FailedJobCleanupTask`** deletes the guarded FAILED rows first (`DELETE ... RETURNING`) and reclaims files only for the ids actually deleted, so a DLQ retry racing the sweep either 404s loudly (row already gone) or rescues a row that still has its candidate file — a storage-first file delete could otherwise orphan a retried job's file, and its diff would moot silently after the operator got a 204. A row deleted before its file could be reclaimed leaves an object the daily orphan/unreferenced sweeps reclaim.
- **`orphanGraceHours` is enforced per project, for row-level orphans**: the baseline-orphan find and its guarded delete embed the same expression — `now() - make_interval(hours => COALESCE(p."orphanGraceHours", DEFAULT_ORPHAN_GRACE_HOURS))` — so a screenshot is reclaimed only after its *own* project's grace, and find and delete cannot disagree by construction. The retention preview reports the same fallback. Object-level orphans cannot read it: an object with no row has no project, so the unreferenced-object sweep keeps the global default window (a store→commit race lasts milliseconds, so the window is a safety margin, not retention).
- **PDF render cache is swept by its own maintenance task**: The `pdf-render/` namespace (rendered page images + page-count blobs, keyed by the source PDF's object name) is not tracked in the DB, so it is not covered by the maintenance deletions above. `PdfRenderCacheCleanupTask` lists the namespace via `IStorageProvider.listObjectsWithLastModified` and evicts any cache whose base PDF object no longer exists (covers PDFs retired by upload-supersede, test/variant deletion, and approval). Approval still evicts the previous baseline's cache eagerly via its `cleanupAfterCommit` hook (through the `PDF_RENDER_CACHE` seam).
- **Deploy note (job-queue columns)**: `ComparisonJob.candidateId` and the variant columns are nullable and backfilled as NULL by `prisma migrate deploy` (schema defaults). Before deploying with unsettled jobs, backfill them from the payload (`UPDATE "ComparisonJob" SET "candidateId" = payload->'candidate'->>'id', "variantViewport" = payload->'variant'->>'viewport', ... WHERE "candidateId" IS NULL AND status IN ('PENDING','PROCESSING','FAILED')`) or drain the queue first — otherwise orphan cleanup may treat a candidate that a job still owns as orphaned.
- **A failed job still owns its candidate**: the CURRENT-orphan sweep treats a candidate referenced by a `PENDING`, `PROCESSING` **or `FAILED`** `ComparisonJob` as not-orphaned — the statuses are one constant (`CANDIDATE_OWNING_JOB_STATUSES`) in `orphaned-screenshot.repository.ts`, used by the find, the delete-time guard and the NULL-candidateId skip. The file is the DLQ retry's input (`FailedJobStore.retry` flips the row back to `PENDING` and the worker re-downloads the payload's candidate URL) and the forensic evidence of the failure, so its retention belongs to `FailedJobCleanupTask` (row first, then the file, after `JOB_RETENTION_DAYS`) and never to the daily sweep. Before this rule the sweep ran first in the same cron pass and reclaimed that object up to a week early, which turned an operator's retry into a silent `completed`.
- **Observability events use primitives**: `ObservabilityEvent` payloads use `string` types (not domain enums from `public/`) to keep `common/` free of reverse dependencies on domain modules.
- **Event payloads reference surviving entities**: Events are built from the committed result of a state change, so payload IDs must reference rows that survive the transaction. The identical-upload path emits no `ScreenshotUploaded` event (no screenshot is stored); the unchanged diff path omits `comparisonId` (no comparison row is created).
- **PrismaConnection vs TransactionContext**: `PrismaConnection` handles client lifecycle; `TransactionContext` provides ALS-based transaction routing for repositories. `PrismaUnitOfWork` composes both. Transaction-aware repositories inject `TransactionContext`; read-only ones inject `PrismaConnection` directly.
- **Deletion uses two cascade models by scope**: Whole-test deletion (`TestDeletionService.deleteTest`) relies on DB-level `onDelete: Cascade` from `UnifiedTest` to variants/screenshots/comparisons — the storage URLs are collected before the delete so files can be removed after commit. Variant-scoped deletion (`deleteScreenshotsByFilters`) must be explicit: it deletes comparisons → screenshots → variants inside a transaction because the DB cascade cannot express "only this variant."
- **Test status recompute is a transactional calling convention**: `UnifiedTest.status` is a persisted aggregate derived from the per-variant rule via `TestStatusService.recomputeStatus` → `VariantStore.findVariantStatusSignals` → `resolveVariantStatusFromComparison` per variant → `resolveAggregateStatusFromVariantStatuses`. Any pending variant makes the whole test PENDING_APPROVAL, any baseline-less variant makes it PENDING, and only a test where every variant is clean reads UNCHANGED — so the persisted row and the per-variant read model (and the PDF details read, which surfaces the shown variant's own status) share one derivation. It is deliberately updated in the SAME transaction as the mutation that changed the underlying facts — there is no event-triggered or post-commit recompute (a triggered design would break the transactionality of the status update). Every mutation path that changes comparisons or screenshots returns a `PersistedChange` from its `StateChangeWorkflow.executeStateChange()` (or `executeWithStoredFile()`) change. The convention is compile-enforced by the `PersistedChange` contract — a mutation that changed domain rows must return `{ kind: 'change', affectedTestIds: [testId, ...] }` (a non-empty tuple, so "forgot the testId" does not compile), a mutation that changed nothing returns `{ kind: 'noop' }`, and a whole-test deletion returns `{ kind: 'deleted' }` (the affected tests no longer exist to name — calling it a "noop" would make the contract lie). A `noop` cannot publish events — an event means something changed, which means a test must be named; a `deleted` cannot either, for the same reason. The workflow recomputes statuses for `change` results in the same transaction right after the change: upload (stored + identical), diff worker (unchanged + within-threshold + diff), approval, threshold update, and variant deletion.
- **Baseline revisions are the undo record, not a second baseline**: `BaselineRevision` rows keep an overwritten baseline's file and metadata so it can be restored; the live baseline stays the single `(testId, variantId, type = BASELINE)` row, and restore rewrites that row in place with the revision's content and threshold. The write happens inside the same `StateChangeWorkflow` transaction as the overwrite (approval or restore), pruning keeps the newest `BASELINE_HISTORY_LIMIT` rows per variant, and the reclaim chain treats revision URLs as references — otherwise the orphan sweep would delete exactly the files the history view serves. Restore retires pending comparisons and queued jobs through `ComparisonRetirementService.supersedeForVariant` (a pending diff was computed against the replaced baseline), rejects inherited variants with `409`, and rejects a revision that already equals the current baseline. Both writers replace the row through the same rule — `BaselineHistoryService.overwriteKeepingHistory`, which snapshots the outgoing baseline and then overwrites it in place, transaction-riding. `recordOutgoingBaseline` is private to that method, so "overwrote a baseline without keeping the history" is unrepresentable rather than something each caller remembers. Auto-accepted within-threshold diffs create no revision: they keep the baseline, so there is nothing to preserve. See ADR-028.
- **Review loop is kind-agnostic and shared**: The frontend review session (`useReviewSession`) walks the pending list for a project (`GET /projects/:projectName/tests/meta/pending`), which mixes image and PDF tests with no kind discriminator. Approve/skip navigates through the `test-detail` route, which dispatches by kind, so the loop lands on and continues through both kinds — PDF detail pages participate in the same session (they query the pending list and delegate approve/skip to it). A module-level seen-set survives page switches within a project so skipped tests are not re-offered mid-pass; it resets on project change or when a test is entered directly rather than via the loop. The pass protocol (seen-set + the `history.state.fromReviewLoop` fresh/continued-pass mark) has a single owner in `frontend/src/lib/review-pass.ts`, composed by both `useReviewSession` and `useTestNavigation` — no other module reads or writes the mark. The mark rides the route entry: a table click or typed deep link starts a fresh pass, while back-navigation restores the mark and continues the pass (already-skipped tests stay skipped); a full reload keeps the mark too, but the in-memory seen-set is re-instantiated empty on reload, so the pass is effectively fresh.
- **Variant gallery is the unfiltered per-variant read**: `GET /projects/:projectName/tests/:testName/variants` returns one row per variant of an image test (identity, baseline/candidate URL, mismatch count, inherited flag), with the status derived by the same `resolveVariantStatusFromComparison` rule as the project overview and the latest comparison picked by the shared status set + ordering. It takes no variant filter: the gallery IS the unfiltered view, and a tile click only changes the route's variant query params (`router.replace`), so the details query refetches that variant while `passMarkState()` keeps the history entry inside the running review pass. The component stays presentational; the page owns the navigation and hides the gallery for single-variant tests. The same read backs the read-only overview page (`/projects/:projectName/tests/:testName/overview`), which shows the BASELINE of every variant as a uniform thumbnail (fixed height, cropped at the bottom so every tile shares one width scale) — no candidate image, no review status — and only links into the comparison. Approve/skip exist only on the review detail page.

## Example Dialogue

**Dev**: When a user uploads a new screenshot, what happens?

**Domain Expert**: The system gets the CURRENT screenshot — the one being uploaded — and pairs it with the existing BASELINE for that UnifiedTest and Variant. If no baseline exists, this first upload becomes the BASELINE and we return BASELINE_CREATED.

**Dev**: So a ComparisonOutcome of BASELINE_CREATED means it's the first time?

**Domain Expert**: Right. If a BASELINE already exists, we first check whether the new image has the same hash as the existing baseline. If it does, we return IDENTICAL immediately — no comparison needed.

**Dev**: And if the hash is different?

**Domain Expert**: Then it gets queued. If a previous comparison was still PENDING_APPROVAL for that variant, we delete it immediately along with its candidate screenshot. Then we store the new CURRENT screenshot and enqueue a new ComparisonJob. The uploader gets COMPARISON_QUEUED back right away.

**Dev**: So the old pending comparison is cleaned up immediately, not later?

**Domain Expert**: Correct. The stale comparison + its candidate screenshot are removed synchronously during upload. The ComparisonJob processes in the background. When the diff finishes, the test status is derived from the latest remaining comparison via `recomputeStatus` (`test-status.policy.ts`) — the same rule for both kinds. A diff with no differences stores no comparison at all, so the test stays UNCHANGED once it has a baseline; a remaining comparison maps to PENDING_APPROVAL. If the comparisons were all deleted during upload, the test returns to its prior state (UNCHANGED with a baseline, PENDING without one). If there are differences, it becomes PENDING_APPROVAL and a reviewer needs to approve the change. There is no reject action — a pending change is retired by the next upload, by a threshold auto-accept, or by deletion (see ADR-023).

**Dev**: What's the daily cron for then?

**Domain Expert**: That's for a different kind of cleanup — orphaned screenshots. Screenshot records in the database that have no matching comparison are cleaned up once a day at midnight by the OrphanCleanupService (a MaintenanceTask).
