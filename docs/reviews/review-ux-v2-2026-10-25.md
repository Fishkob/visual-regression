# Review UX & v2 Follow-Up — 2026-10-25

Read-only product/UX and technical review of the R18–R20 surfaces after the
roadmap was completed. Three independent reviews (comments/reasons,
assignments/4-eyes, technical follow-ups) inspected code only; no runtime
behavior beyond what is cited was exercised. This document consolidates their
findings and proposes a v2 backlog.

Scope: comments, approval reasons, 4-eyes votes, assignments, "My reviews",
SLA/overdue, share links, and the new lifecycle/audit paths.

## Strengths

- 4-eyes is server-authoritative: unique comparison+reviewer vote, retried
  Serializable workflow, repeat vote → 409, N=1 keeps the legacy path.
- Votes are never reported as approvals on single, bulk, run or test-level
  paths; the UI checks `pending` before claiming success.
- Comments are plain text end-to-end (no `v-html`), body capped and validated,
  comparison ownership checked before write.
- Share tokens are 256-bit, SHA-256 at rest, revocable/expiring, passphrase
  scrypt-hashed, resolved by POST behind the login rate limit.
- Approval finalization is atomic with audit + webhook outbox; webhooks are
  SSRF-guarded, HMAC-signed and deduplicable.
- New migrations are additive, indexed and FK-safe; i18n keys are at parity.

## P2 highlights

- Comment resolve is one-click/irreversible in UI; no undo, pending state or
  unresolve; composer lacks a real label/`aria-describedby`.
- Approval dialog has no pending/inline-error state; double Enter can double
  submit.
- Approval history lacks variant labels and error states; audit page cannot
  label/filter the new actions.
- Assignment creation uses free-text usernames, allows VIEWER/inactive users and
  past due dates, has no unassign/reassign/duplicate guard, and does not
  auto-complete on approval.
- Overdue is a dead-end count with no link/filter/per-row due date.
- Share access audit is unbounded; passphrase minimum is 4 and failed attempts
  are not logged; revoke is unscoped and re-audits idempotent calls.
- No unit specs for share/assignment/comment services and several e2e gaps
  (RUN share, deleted-project share, duplicate assignment, N=3, concurrent last
  vote, threshold bypass).
- Quality/axe cases do not render populated comments, resolved rows or the
  approval/assign dialogs.

## Quick wins (≈ ≤1 day each)

1. ADMIN-gate + audit `requiredApprovals` and threshold changes (with
   from/to, same transaction).
2. Reject API-key approvals when `requiredApprovals > 1`; unique API-key names;
   audit every vote.
3. Delete comments/votes with the test and add a retention sweep.
4. Reclaim stale `PROCESSING` webhook deliveries.
5. Comment list newest-first (keep latest 200).
6. Add reason/note to approval audit metadata and the approved webhook.
7. Fix default-branch assignment matching (branch id or resolved name).
8. Thread `assignedToMe` through URL, pending query and review count.
9. Add `review.assigned`/`review.comment` to the webhook picker + labels with
   enum-parity test.
10. Correct 4-eyes bulk copy and `pendingToast` wording; collapse comments when
    empty and move the panel below the diff.
11. Add new audit actions to the audit page labels/filter.
12. Add quality cases for comments (populated/resolved), the approval dialog and
    the assignment badge.

## Product decisions needed

1. Is a thread test-wide or comparison-scoped, and should inherited tests share
   the owning branch's thread?
2. Should unresolved comments block, warn, or be a project setting?
3. May an uploader approve their own change in 4-eyes? Are API keys ever allowed
   to vote for N>1?
4. Does each vote carry its own reason, and may a reason be corrected later?
5. What happens to in-flight votes when `requiredApprovals` changes?
6. Is "Mark complete" self-attestation or a gate; should approval auto-complete?
7. Are run assignments in scope; where do they surface?
8. Are VIEWERs allowed to comment/resolve or be assigned?
9. Fixed reason taxonomy or per-project values?
10. Bulk approval stays reason-less — should the UI state that explicitly?

## Implemented follow-up (2026-11-16)

ADR-041 implements the first increments:

- Review policy (`requiredApprovals`) moved to an ADMIN-only, audited endpoint;
  the generic project PATCH rejects the field.
- Pixel threshold changes are ADMIN-only and audited with previous values and
  the auto-accepted count.
- 4-eyes approvals are human-only: API keys are rejected for N>1, votes are
  keyed by principal id, partial votes write `review.vote`, and API-key names are
  unique (rotation renames the predecessor).

Still open from this review: vote visibility/read model, share-link ids,
webhook lease, lifecycle cleanup, "My reviews" threading, default-branch badge,
comments placement/pagination and the UX/copy items.

## Recommended first increment

1. Policy gate + audit (P1 #2) — smallest change with the largest governance
   payoff.
2. Human-only 4-eyes (P1 #1) — close the API-key bypass and audit each vote.
3. Silent-loss fixes: lifecycle cleanup (P1 #4), webhook lease (P1 #5),
   newest-first comments (P1 #6), reason in audit/webhook (P1 #12).
4. UX correctness: default-branch assignment (P1 #10), My reviews threading
   (P1 #11), comments placement (P1 #7), bulk/pending copy (P1 #12).
